Look for correctness problems: bugs, crashes, data loss, security holes, a broken build or tests, and anything that doesn't do what the task asks. Read the surrounding code where you need to. If you have a code review skill or command (such as /code-review), use it.

Decide how serious a problem is by what it does to someone using the result, not by what kind of problem it is: if the change makes something that worked before work worse (slower or more costly on a path that runs all the time counts), or if what the task asks for does not happen in a state that ordinary use leads to, it must be fixed before merging even when it looks like only performance or an edge case, because a minor issue may be merged as it is; keep as minor what needs an unusual setup to reach or only leaves the new work less polished.
