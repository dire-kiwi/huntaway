## What it shows

1. **Nothing was missed.** In all 27 reviews every expected issue was named. The answer key holds only problems that a
   review on the board had already found, and a reviewer reading the code finds them again. So this key cannot show a
   change that makes reviews find more. It can only show how they rank what they find.
2. **The ranking is what varies, and it varies between runs of the same instructions.** `a` and `b` differ on HE-85:
   one sent it back to be fixed, the other passed the change with the fault as a minor note. Four more reviews under
   v1 (see below) ranked HE-84's issue serious once and minor once, and HE-85's minor. A review that passes with the
   fault as a minor note leaves it unfixed, since only serious issues go back to the task's agent.
3. **The candidate moved its target and lost elsewhere.** It was written to raise HE-59 issue 2 and HE-64 issue 2. It
   raised the first, left the second, and ranked three others lower than both runs of v1 did. Its closing clause
   ("keep as minor what needs an unusual setup to reach") shows in the reasons its reviews give for ranking a known
   problem down: "needs an unusual server" (HE-85), "a narrow race" (HE-90). A difference of two or three issues is not far outside the one-issue difference between `a` and `b`, so the
   honest reading is "no better, probably worse".
4. **HE-64 issue 2 was minor in every review.** The board's second round of review called it serious. Either the
   reviewers under-rank it or the key over-ranks it: a person should decide, and say so in the key.

## Problems the reviews raised that are not in the key

Not judged by the grader. Both describe code that is still in `main` as of `04b8d12`.

- **HE-59, in all four of its v1 reviews and in the candidate's**: the fallback mark is cleared by comparing model ids
  as text (`apps/server/src/runs/claude/output.ts`, `to !== effect.model`), and `modelName`
  (`packages/contracts/src/task.ts`) does not accept an id ending in `[1m]`. If Claude Code names the fallback model
  with `[1m]` on a 1M-context session, the badge goes at the fallback model's first reply. The reviewers inferred that
  from reading Claude Code's bundle; nobody has seen such a line.
- **HE-94, minor in `a` and `b`, serious in `c`**: with "Create a GitHub repository for it" ticked, the folder is
  made by `GithubRepos.create` with a plain `git init -q`, so it gets no README and no first commit
  (`apps/server/src/github/GithubRepos.ts`).

## Departures from the method

- Four of the first reviews failed on API overload (18 were started at once). Their re-runs were first started with one
  more sentence in the launch message, asking for a short final message. Those four were set aside and run again with
  the same launch message as the rest. The set-aside four are the "four more reviews under v1" above: HE-59 (same
  grades as `a` and `b`), HE-84 twice (minor and pass; serious), and HE-85 (minor and pass).
- Reviews ran as subagents of the session that ran the round, on its model, reading only (see the README).

## Cost

31 reviews, two gradings and one coach: about 3.5 million tokens in subagents, and about an hour and a half.

## Next

- The key needs rows that reviews got wrong: a change that passed review on the board and was then found broken. None
  of the nine rows is one. The fixes made after a merge in this repository so far mostly trace back to the large port
  pull requests, which are too big to replay.
- With this key, the question the scores can answer is how much one review can be relied on, not which wording is
  better. Under v1 a single review passed a change with a known problem in 3 of the 18 row runs that had one (the
  four set-aside reviews included). That is a case for the two reviewers the project already has, and a way to test
  whether a cheaper reviewer set-up finds as much.
